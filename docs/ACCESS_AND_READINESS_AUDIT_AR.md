# CraftMate AI — خريطة الصلاحيات والجاهزية

**الغرض:** تحديد ما يمكن تنفيقه من مساحة العمل مباشرة، وما يحتاج جلسة مالك الحساب مرة واحدة، وما لا يجب أن يمر عبر المحادثة أبداً. هذه الخريطة تمنع الطلبات المتفرقة وتوضح حدود كل نظام.

## نتيجة الفحص العام الآمن

تم الفحص دون استخدام أي سر ظهر في المحادثة:

| النظام | الحالة المثبتة | الدليل الآمن |
|---|---|---|
| GitHub Repository | متاح للقراءة العامة | `SAYED1135/CraftMate-AI` يرد بنجاح، و Release `v0.3.0` موجود |
| GitHub Pages | حي | الصفحة الرئيسية و`app.html` تردان بنجاح |
| Cloudflare Worker | حي ومعدّ | `/health` يعيد `configured:true` |
| Worker Claim | يصل لقاعدة البيانات | كود وهمي يعيد `INVALID_CODE` بدل خطأ خادم |
| Supabase Auth | حي | Auth health يعيد نجاحاً |
| Supabase Plans | حي | خطط Free/Pro/Ultra مقروءة بالمفتاح العام الآمن |
| Plugin | مبني محلياً | JAR للإصدارين 0.3.0 و0.3.1 موجودان في مساحة العمل |

## ما أستطيع تنفيذه مباشرة

- تعديل كود الموقع واللوحة والبلجن والـ Worker والوثائق والهجرات.
- بناء واختبار البلجن وإنتاج JAR.
- فحص الواجهات العامة والـ Worker وSupabase بالمفاتيح العامة فقط.
- تجهيز سكربتات الإعداد والنشر والاختبار.
- تجهيز إصدارات كاملة بملفاتها وملاحظاتها عندما تتوفر قناة نشر مصرح بها.

## ما يحتاج جلسة مالك مرة واحدة

هذه ليست مفاتيح تُرسل في المحادثة؛ هي جلسات أو إدخال مخفي في الجهة الرسمية:

| المهمة | الطريقة الصحية | التكرار |
|---|---|---|
| رفع الكود وإنشاء Release | تسجيل دخول GitHub على جهاز المالك أو ربط GitHub الرسمي | عند النشر |
| تغيير Worker أو أسراره | `wrangler login` أو سكربت الإصلاح المخفي | عند تغيير البنية/السر |
| تنفيذ هجرات SQL ذات DDL | Supabase SQL Editor أو Supabase CLI بجلسة المالك | عند تغيير قاعدة البيانات |
| إعداد SMTP للبريد | لوحة Supabase و Resend من حساب المالك | مرة واحدة قبل الإطلاق |

## ما لا أستلمه في المحادثة

- مفتاح Supabase `service_role` أو أي Secret Key رئيسي.
- Cloudflare API Token واسع الصلاحية.
- GitHub Personal Access Token.
- كلمات مرور الحسابات أو أكواد التحقق.

أي قيمة من هذه ظهرت في محادثة أو لقطة تعتبر مكشوفة ويجب تدويرها/حذفها. هذا لا يمنع العمل؛ يمنع فقط تخزين سر السيطرة خارج مكانه الرسمي.

## ملاحظة سبق توضيحها

النظام لا يعمل بـ صلاحية واحدة سحرية:

- المفتاح العام في الموقع مخصص للقراءة/الكتابة المقيدة بـ RLS.
- الـ Worker وحده يحتاج سراً عالي الصلاحية لعمليات الربط.
- GitHub مسؤول عن الكود والإصدارات، لا عن بيانات المستخدمين.
- Cloudflare مسؤول عن واجهة البلجن الآمنة، لا عن استضافة سيرفر Minecraft.
- مالك الاستضافة وحده يرفع البلجن ويعيد تشغيل سيرفر اللعبة.

## عوائق حقيقية حالياً

1. إصلاحات لوحة الربط الأخيرة وخطة إعادة التأسيس محفوظة في مساحة العمل ولم تُنشر بعد إلى GitHub Pages.
2. بلجن v0.3.1 مبني محلياً ولم يتحول بعد إلى GitHub Release رسمي.
3. تشغيل Migration 004 والتحقق من الأعمدة يحتاج جلسة Supabase مالك أو دليل نتيجة SQL.
4. إعداد SMTP الإنتاجي لم يتم بعد، لذلك بريد Supabase الافتراضي غير مناسب لإطلاق عام.
5. لا توجد بعد بيئة Staging منفصلة أو بوابة اختبار نهاية لنهاية إلزامية قبل النشر.

## قاعدة العمل المعتمدة

كل مهمة قادمة يجب أن تذكر من البداية: الكود المطلوب، الاختبار، قناة النشر، وهل تحتاج إجراء مالك واحداً أم لا. لا طلبات سرية مفاجئة في منتصف التنفيذ.
