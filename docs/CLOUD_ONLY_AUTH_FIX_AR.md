# إصلاح التسجيل السحابي — Cloud-Only Auth

**التاريخ:** 2026-10-16  
**Build اللوحة:** `2026.10.16-cloudonly2`  
**Worker:** CraftMate Connector API `0.4.0`

## المشكلة

Supabase المدمج لإرسال البريد مخصص للتجربة وحدّه رسالتان في الساعة للمشروع كله. لذلك كان التسجيل العادي عبر `/auth/v1/signup` مع تفعيل **Confirm email** يفشل أحيانًا برسالة:

```text
email rate limit exceeded
```

وكان التطبيق يعرض للمستخدم مخرجًا جانبيًا اسمه «الدخول الفوري» المحلي. هذا يتعارض مع هدف المنتج: الحسابات والبيانات الأساسية يجب أن تكون سحابية.

## القرار

أصبحت المنصة **Cloud-Only** في المصادقة:

- لا يوجد زر «دخول فوري» محلي.
- لا يوجد حساب تجريبي محلي من شاشة الدخول.
- أي جلسة قديمة `mode: local` تُرفض عند فتح التطبيق ويُطلب تسجيل الدخول سحابيًا.
- لا يستطيع المستخدم لصق Supabase URL أو مفتاح من المتصفح؛ الاتصال ثابت بإعداد المنصة العام الآمن للمتصفح.
- إعدادات التطبيق تعرض حالة السحابة والمزامنة فقط، من دون زر إيقاف الوضع السحابي.

## مسار التسجيل الجديد

```text
المتصفح
  ├─ POST /v1/auth/register  → Cloudflare Worker (خادم موثوق)
  │                              └─ Supabase Auth Admin API
  │                                 create user with email_confirm=true
  └─ POST /auth/v1/token      → Supabase Auth (تسجيل دخول عادي بالبريد وكلمة السر)
```

النقطة الأساسية: إنشاء المستخدم من **Admin API** لا يرسل رسالة تأكيد، ويمكنه إنشاء الحساب مؤكدًا بـ `email_confirm=true`. لذلك لا يمر التسجيل الجديد بمزوّد البريد المدمج صاحب حد الرسالتين/ساعة أصلًا.

المتصفح لا يرى `service_role` أبدًا. المفتاح السري يبقى في Cloudflare Worker Secret باسم `SUPABASE_SERVICE_ROLE_KEY` فقط.

## حماية نقطة التسجيل

في `POST /v1/auth/register` بالـ Worker:

- تحقق صارم من اسم المستخدم والبريد وكلمة سر 8–72 حرفًا.
- رفض اسم مستخدم موجود في `profiles` قبل إنشاء الحساب.
- Honeypot مخفي ضد البوتات البسيطة.
- حد مبدئي: 10 محاولات تسجيل في الساعة لكل IP داخل نسخة الـ Worker.
- رسائل خطأ ثابتة مثل `USERNAME_TAKEN` و`ACCOUNT_EXISTS` بدل تسريب أخطاء Supabase الخام.
- لا تُسجل كلمات السر أو مفاتيح الخدمة في السجلات.

> **مقايضة بيتا واعية:** `email_confirm=true` يعني أننا لا نتحقق فعليًا من ملكية البريد عند إنشاء الحساب في مرحلة الإطلاق المغلقة. هذا مقبول مؤقتًا لتجربة المنتج، لكنه ليس النموذج الإنتاجي النهائي.

## النشر الوحيد المطلوب من المالك

الكود والموقع يُنشران من GitHub، لكن الـ Worker الحالي على Cloudflare لن يحصل على نقطة `/v1/auth/register` إلا بعد إعادة نشره.

اللوحة الآن تفحص `/health` أولًا. إذا لم تجد `auth_registration:true` ولم يكن Native Signup مضمونًا من دون بريد، فإنها **لا ترسل محاولة Signup أصلًا** ولا تستهلك حد بريد Supabase ولا تقفل التسجيل بعدّاد متصفح قديم. عدّاد الـ 60 ثانية أصبح خاصًا بزر إعادة إرسال البريد للحسابات القديمة فقط.

### أسرع تفعيل من PowerShell

شغّل الأمر التالي مرة واحدة. هيحمّل آخر نسخة من المستودع إلى مجلد مؤقت وينفّذ سكربت النشر:

```powershell
Set-ExecutionPolicy -Scope Process Bypass -Force; irm https://raw.githubusercontent.com/SAYED1135/CraftMate-AI/main/worker/bootstrap-cloud-auth.ps1 | iex
```

أو من جذر مستودع محلي محدّث:

```powershell
powershell -ExecutionPolicy Bypass -File .\worker\deploy-cloud-auth.ps1
```

السكريبت:

1. يتحقق من تسجيل دخول Wrangler.
2. يتحقق فقط من وجود Secret بالاسم `SUPABASE_SERVICE_ROLE_KEY`، ولا يقرأ قيمته ولا يطبعها.
3. ينشر الـ Worker.
4. ينتظر حتى يرجع `/health` بالقيم `version=0.4.0` و`auth_registration=true` و`configured=true`.

إذا قال السكريبت إن الـ Secret غير موجود، شغّل `worker/fix-connector.ps1` أولًا وأدخل المفتاح **المُدوّر** في موجه الإدخال المخفي فقط. لا تلصق أي مفتاح سري في المحادثة أو GitHub.

## بوابة قبول التسجيل

بعد نجاح السكريبت:

1. افتح `app.html` من نافذة خاصة/متصفح نظيف حتى لا تختلط الجلسات القديمة.
2. أنشئ حسابًا ببريد جديد لم يُستخدم في محاولة غير مؤكدة سابقة.
3. المتوقع: دخول مباشر إلى اللوحة من دون رسالة بريد.
4. سجّل خروج ثم دخول بنفس البريد وكلمة السر.
5. أنشئ سيرفرًا تجريبيًا وسجل خروج/دخول؛ يجب أن يعود السيرفر من السحابة.
6. جرّب نفس البريد مرة أخرى في التسجيل؛ يجب أن تظهر رسالة «فيه حساب سحابي بالبريد ده».

## ماذا عن الحسابات القديمة غير المؤكدة؟

الحسابات التي أُنشئت سابقًا عبر signup العادي وبقيت غير مؤكدة لا يؤكدها endpoint الجديد تلقائيًا، لأن إنشاء نفس البريد سيرجع `ACCOUNT_EXISTS`. أمامها مساران:

- المستخدم يفتح رسالة التأكيد القديمة أو زر «إعادة إرسال تأكيد البريد (للحسابات القديمة)» مرة واحدة، مع الانتباه أن الإعادة ما زالت تستخدم البريد.
- أو المالك يحذف/يؤكد المستخدم يدويًا من Supabase Authentication → Users إذا كان حساب اختبار معروفًا.

لا تستخدم بريدًا عالقًا في أول اختبار قبول للإصدار الجديد.

## مسار الإنتاج النهائي

قبل الإطلاق العام يجب الانتقال من التأكيد التلقائي إلى تحقق بريد حقيقي:

1. إعداد Custom SMTP (مثل Resend) في Supabase.
2. رفع حد Auth **Emails sent per hour** من القيمة الابتدائية.
3. إعادة تفعيل/إبقاء **Confirm email**.
4. جعل التطبيق يستخدم Native Supabase Signup أولًا أو تعطيل `email_confirm=true` في مسار الـ Worker.
5. إضافة Turnstile/CAPTCHA وحدود تسجيل أقوى على مستوى Cloudflare قبل فتح التسجيل العام.

بهذا يبقى التسجيل الحالي مناسبًا للبيتا المغلقة من دون حد الرسالتين، بينما يظل التحقق الكامل بالبريد هو بوابة الإنتاج.
