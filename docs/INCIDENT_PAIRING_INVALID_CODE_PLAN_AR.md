# حادثة `INVALID_CODE` — تحقيق وخطة إصلاح شاملة

## الخلاصة التنفيذية

رسالة البلجن:

```text
Connector API HTTP 404: INVALID_CODE
```

تعني أن البلجن وصل إلى Cloudflare Worker، وأن الـ Worker بحث في Supabase ولم يجد صفاً مطابقاً لكود غير مُبطَل. المشكلة ليست في اتصال البلجن بالإنترنت ولا في عنوان الـ API هذه المرة.

## ما تم اختباره بأنفسنا

تم تشغيل لوحة التحكم في متصفح Headless مع محاكاة Supabase ومراقبة الطلبات:

| السيناريو | النتيجة قبل الإصلاح | النتيجة بعد الإصلاح |
|---|---|---|
| سيرفر محلي يتحول لسيرفر سحابي ثم إصدار كود | ناجح عند اكتمال الطلبات | ناجح وتم التحقق من وجود الصف |
| كود محفوظ محلياً بحالة `cloudSyncing=true` من جلسة سابقة | يعلق ولا يرسل الكود أبداً | تم إصلاحه؛ حالة التزامن أصبحت ذاكرة مؤقتة فقط |
| Supabase يرفض الإدراج بسبب RLS | الخطأ يظهر في اللوحة | يظهر مع Build ID وزر إعادة محاولة |

### عيب مؤكد تم إصلاحه

كانت حالة `cloudSyncing` تُحفظ في `localStorage`. إذا أُغلقت الصفحة أو تعطّلت أثناء التفعيل، يعود الكود بنفس الحالة في الجلسة التالية فتظن اللوحة أن التفعيل ما زال جارياً ولا ترسله أبداً.

الإصلاح في Build `2026.10.16-pairing3`:

- تصفير `cloudSyncing` عند كل تحميل.
- تتبع العمليات الجارية في ذاكرة الصفحة فقط (`codeSyncInFlight`).
- بعد إدراج الكود، تعيد اللوحة قراءته من Supabase ولا تعرض ✅ إلا إذا وجدته فعلياً.
- إظهار رقم البناء داخل حالة الكود لمعرفة هل المتصفح يستخدم النسخة الحديثة أم نسخة مخبأة.

## فرضيات الإنتاج المرتبة

1. **حالة تفعيل عالقة أو نسخة لوحة قديمة في المتصفح** — تم علاجها وإضافة Build ID.
2. **رفض RLS عند إدراج `connector_tokens`** — ستظهر الآن رسالة `Supabase 403` في اللوحة، وتم إعداد Migration 005 لسياسات إدراج/قراءة صريحة.
3. **الكود أُنشئ في الوضع المحلي أو لسيرفر غير محفوظ سحابياً** — اللوحة الآن تمنع اعتبار الكود حقيقياً في الوضع المحلي وتهاجر السيرفر سحابياً قبل الكود.
4. **Migration 004 غير منفذة** — لا تفسر 404 الحالي، لكنها قد تسبب فشلاً لاحقاً عند أول Claim ناجح؛ لذلك تبقى بوابة إلزامية.
5. **عيب في البلجن** — غير مرجح في هذه الرسالة تحديداً؛ البلجن أرسل الكود وحصل على رد JSON من الـ Worker. ما زال يحتاج اختبار عقد Claim في خطة الاختبار.

## خطة الحل النهائية

### المرحلة A — إصلاح فوري منشور

- نشر Build `2026.10.16-pairing3` إلى GitHub Pages.
- تشغيل Migration 005 في Supabase لتوضيح RLS الخاص بأكواد الربط.
- التأكد من Migration 004 قبل أي Claim حقيقي.
- عند توليد كود جديد يجب أن تظهر ✅ مع رقم البناء قبل تنفيذ أمر ماينكرافت.

### المرحلة B — نقل إصدار الأكواد إلى الـ Worker

الحل التجاري الأقوى هو ألا ينشئ المتصفح صف الكود مباشرة تحت RLS. سيتم:

- إضافة مسار Worker جديد لإصدار كود الربط بعد التحقق من جلسة المستخدم وملكية السيرفر.
- إبطال الأكواد غير المستخدمة السابقة لنفس السيرفر ذرياً قدر الإمكان.
- إرجاع الكود للوحة بعد حفظه فقط.
- إضافة مسار حالة لا يستهلك الكود، لعرض: موجود، منتهٍ، مستخدم، مُبطَل، أو غير موجود.

هذا يحتاج نشر Worker عبر GitHub Actions بعد إعداد أسرار Cloudflare المحدودة في GitHub.

### المرحلة C — بوابة اختبار إلزامية

لا إصدار ربط جديد دون:

- اختبار متصفح آلي بمحاكاة Supabase (نجاح، حالة عالقة، ورفض RLS).
- اختبار Worker آلي بمحاكاة Supabase (إصدار، Claim، رفض إعادة الاستخدام، انتهاء، إبطال).
- اختبار بلجن على Paper محلي/تجريبي وسجل محفوظ.
- اختبار حساب QA حقيقي منفصل عن حسابات المستخدمين، دون لمس كود مستخدم حقيقي.
- تقرير إصدار يذكر البناء والهجرات وحالة `/health` ونتيجة الرحلة كاملة.

## معيار إغلاق الحادثة

تغلق الحادثة فقط عندما تنجح الرحلة التالية على سيرفر حقيقي:

حساب سحابي → إنشاء سيرفر → كود تظهر عليه ✅ → `/craftmate link` ناجح → `/craftmate status` مرتبط → `/craftmate sync` → `/craftmate diagnose` → `/craftmate disconnect` يبطل الرمز.
