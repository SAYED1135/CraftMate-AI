# CraftMate AI — خطة إعادة التأسيس الهندسية والتجارية

**حالة المشروع:** تجميد فوري لأي ميزات جديدة حتى اكتمال بوابة الاستقرار الأساسية.  
**القرار:** لا نبدأ من الصفر بالكامل، ولا نكمل البناء فوق الفوضى. سنحتفظ بالأصول الصالحة، ونعيد تأسيس العقود والبيانات والاختبارات والنشر بطريقة تجارية منظمة.
**تحديث 2026-10-16:** بعد نجاح أول ربط حقيقي، أصبح ترتيب الإصدارات وبوابات القبول الحالية موثقًا في `PRODUCT_ROADMAP_AND_EXECUTION_PLAN_AR.md`، وهي المرجع الأحدث عند تعارض ترتيب التنفيذ.

---

## 1. تعريف المنتج الصحيح

CraftMate AI منصة تجارية لمساعدة مالك سيرفر Minecraft على إدارة سيرفره من مكان واحد، على أي استضافة يستطيع الوصول فيها إلى السيرفر بدرجة كافية.

### القيمة الأساسية

- ربط السيرفر بالحساب بأمان.
- معرفة حالة السيرفر واللاعبين والرام والإضافات والنسخة لحظياً.
- تشخيص السجلات والأعطال بلغة بسيطة وخطوات إصلاح.
- تعديل إعدادات وملفات السيرفر بطريقة مقيدة وآمنة وقابلة للتراجع.
- إدارة الإضافات والنسخ الاحتياطية والتنبيهات.
- دعم Java وBedrock عبر Geyser/Floodgate حيثما أمكن.
- مسارات بديلة عند غياب البلجن: رفع السجلات، SFTP، أو تعليمات لوحة الاستضافة.

### حدود أمان لا يتم تجاوزها

- لا تنفيذ أوامر Shell عشوائية من الموقع.
- لا فتح RCON أو منافذ إضافية باسم الراحة.
- تعديل الملفات يبدأ بملفات وإعدادات مسموحة فقط، مع نسخة احتياطية وسجل تدقيق وتراجع.
- أي مهمة من اللوحة إلى السيرفر يجب أن تكون موقعة/موثقة، محدودة النوع، وقابلة للتتبع.

---

## 2. من هو المستخدم؟

المستخدم الأساسي هو مالك سيرفر Minecraft قد يكون مبتدئاً تماماً. لا يفترض المنتج أنه يعرف ما هو Supabase أو Cloudflare أو Worker أو RLS.

### قواعد تجربة المستخدم

- العربية أولاً، والإنجليزية كاملة وليست ترجمة ناقصة.
- كل خطوة لها حالة واضحة: لم تبدأ، جارية، نجحت، فشلت مع سبب بسيط وزر تصحيح.
- لا تظهر أخطاء تقنية خام مثل أسماء جداول أو مفاتيح أو أكواد مزود الخدمة.
- كل خطأ للمستخدم له رقم مرجعي ورسالة مفهومة وخطوة تالية واحدة.
- الوضع التجريبي المحلي منفصل بوضوح عن الحساب السحابي الحقيقي، ولا يصدر أكواد ربط حقيقية.

---

## 3. تشخيص الوضع الحالي بصراحة

### أصول صالحة للاحتفاظ بها

- فكرة المنتج وPRD والهوية الأولية.
- الموقع التعريفي ولوحة التحكم كنماذج واجهة قابلة للتطوير.
- بلجن Paper/Purpur ووظائف اكتشاف البيئة وتنقية السجلات.
- Cloudflare Worker كوسيط آمن بين البلجن وقاعدة البيانات.
- Supabase كمصدر للحسابات وقاعدة البيانات.
- ملفات تعريف الاستضافات الأربع كنقطة بداية.

### عيوب تأسيسية يجب علاجها قبل أي ميزة جديدة

1. تطور المنتج كان تفاعلياً مع الأخطاء بدل بوابات إصدار مخططة.
2. وجود وضعين محلي وسحابي أدى لاختلاف البيانات وأكواد ربط لا تصل إلى السحابة.
3. أخطاء الحفظ السحابي كانت صامتة في بعض المسارات، فظهرت أكواد غير قابلة للاستخدام.
4. إنشاء سجل السيرفر لم يكن متوافقاً دائماً مع UUID في قاعدة البيانات.
5. لا توجد بيئة تجريبية منفصلة ولا اختبار نهاية لنهاية إلزامي قبل الإصدار.
6. إعداد البريد الافتراضي من Supabase غير مناسب لمستخدمين حقيقيين ويسبب حداً منخفضاً جداً للإرسال.
7. إدارة الإصدارات والأسرار والنشر كانت يدوية أكثر من اللازم.
8. التطبيق الحالي ملف واجهة كبير يحتاج تفكيكاً تدريجياً حتى يمكن صيانته واختباره.

## 4. المعمارية المستهدفة

| الطبقة | التقنية المعتمدة | السبب |
|---|---|---|
| مستودع الكود والإصدارات | GitHub + GitHub Actions | مصدر واحد للحقيقة، بناء واختبار ونشر قابل للتتبع |
| واجهة الويب الحالية | تثبيت مؤقت ثم تفكيك تدريجي | عدم إهدار الموجود، مع وقف نمو ملف واحد ضخم |
| واجهة الجيل التالي | Vite + TypeScript + React داخل `web/` عند بدء إعادة البناء | مكونات واختبارات ومسارات وصيانة تجارية |
| الحسابات وقاعدة البيانات | Supabase Auth + PostgreSQL + RLS | حسابات وبيانات وصلاحيات دون بناء خادم تقليدي |
| واجهة البلجن البرمجية | Cloudflare Worker | مكان وحيد آمن للعمليات ذات الصلاحية العالية ورموز السيرفرات |
| البريد | Resend عبر Supabase Custom SMTP قبل أي إطلاق عام | تجاوز حد بريد Supabase الافتراضي وتحسين التسليم |
| بلجن السيرفر | Java/Gradle لـ Paper/Purpur | يعمل داخل سيرفر المستخدم ويرسل طلبات صادرة فقط |
| الاختبارات | اختبارات وحدات + Worker + واجهة + اختبار Paper حقيقي | لا إصدار يعتمد على التجربة اليدوية وحدها |
| السجلات والأخطاء | معرفات أخطاء وسجلات منظمة وصفحة حالة | دعم المستخدم دون كشف تفاصيل البنية الداخلية |

### لماذا Supabase موجود أصلاً؟

المستخدم لا يتعامل مع Supabase مباشرة. هو بالنسبة إلى CraftMate:

- مكان حسابات المستخدمين وتسجيل الدخول.
- قاعدة بيانات السيرفرات والتقارير والتنبيهات وأكواد الربط.
- نظام صلاحيات يمنع مستخدماً من رؤية بيانات مستخدم آخر.

أي مشكلة فيه، مثل حد إرسال البريد، هي مسؤولية إعداد المنتج وليست شيئاً يجب أن يفهمه المستخدم العادي أو يصلحه.

## 5. نموذج دعم الاستضافات

المنتج Host-Agnostic، والاستضافات تصنف حسب قدرات الوصول لا حسب اسم الشركة فقط:

| المستوى | القدرة | تجربة CraftMate |
|---|---|---|
| Tier A | رفع بلجن + ملفات + كونسول | ربط كامل، حالة، تشخيص، مهام إعدادات آمنة |
| Tier B | بلجن من متجر داخلي أو وصول ملفات محدود | ربط موجه حسب الاستضافة |
| Tier C | SFTP/FTP أو رفع سجلات فقط | تشخيص ومساعدة ملفات دون ربط لحظي |
| Tier D | لوحة مغلقة تقريباً | Wizard وتعليمات وقيود معلنة بصراحة |

الاستضافات الأربع الحالية تبقى أدلة عميقة أولى: Play.hosting وFalixNodes وMCServerHost وMinefort، لكن البلجن والتشخيص لا يتوقفان عليها.

## 6. خطة التنفيذ ببوابات قبول

### المرحلة 0 — التجميد والتدقيق

- إيقاف الميزات الجديدة.
- اعتماد هذه الخطة وسجل العيوب.
- مراجعة الأسرار والصلاحيات والنسخ والإصدارات.
- تحديد بيئات التطوير والتجربة والإنتاج.

**بوابة الخروج:** قائمة عيوب مرتبة، ومالك لكل بند، ومعيار قبول مكتوب.

### المرحلة 1 — التأسيس

- تنظيف المستودع وفروع العمل وإصدارات الملفات.
- فصل الإعدادات العامة عن الأسرار.
- توثيق كل متغير بيئة ومكان تخزينه ومالكه وتاريخ تدويره دون كتابة قيمته.
- إنشاء بيئة تجريبية منفصلة للوحة والـ Worker وقاعدة البيانات.
- رسائل أخطاء موحدة للواجهة والبلجن والـ Worker.

**بوابة الخروج:** نشر تجريبي قابل للتكرار من خطوات مكتوبة، دون مفاتيح في الكود أو المحادثة.

### المرحلة 2 — إثبات المسار الأساسي نهاية لنهاية

المسار الإلزامي:

1. إنشاء حساب وتسجيل دخول.
2. إنشاء سيرفر.
3. توليد كود ربط لا يظهر كجاهز قبل حفظه سحابياً.
4. تثبيت البلجن وتنفيذ `/craftmate link`.
5. ظهور السيرفر Online من نبضة حقيقية.
6. تنفيذ `/craftmate sync` و`/craftmate diagnose`.
7. فصل السيرفر وإبطال رمزه.

**بوابة الخروج:** نجاح المسار على سيرفر Paper حقيقي وسيرفر استضافة مجانية واحد على الأقل، مع سجل اختبار محفوظ.

### المرحلة 3 — إدارة السيرفر الآمنة

- قائمة ملفات/إعدادات مسموحة للقراءة والتعديل.
- نسخة احتياطية قبل التعديل وتراجع من اللوحة.
- مهام موقعة يسحبها البلجن وينفذها محلياً ويعيد نتيجتها.
- سجل تدقيق لكل تغيير.
- إدارة حالة الإضافات في حدود ما تسمح به بيئة Paper.

**بوابة الخروج:** تعديل إعداد حقيقي من اللوحة، ظهوره على السيرفر، ثم التراجع عنه بنجاح.

### المرحلة 4 — التشخيص والتنبيهات والدعم

- توسيع بصمات الأعطال واختباراتها.
- تقارير مفهومة للمبتدئ مع خطوات مرتبة حسب الاستضافة.
- تنبيهات توقف وسبات وتشخيص عالي الخطورة.
- دعم داخل المنتج يستخدم رقم الخطأ وسجل الحالة، لا يطلب أسراراً من المستخدم.

### المرحلة 5 — الإطلاق التجريبي المحدود

- بريد إنتاج عبر Custom SMTP.
- صفحات قانونية وخصوصية وحذف حساب وتصدير بيانات.
- مراقبة أخطاء وحدود استخدام ونسخ احتياطي.
- مجموعة صغيرة من المختبرين الحقيقيين ومعايير قبول مكتوبة.

### لاحقاً فقط

- Crossplay Wizard أوسع.
- المدفوعات والخطط المدفوعة بعد إثبات القيمة.
- بوت AFK خارج نطاق المنتج بقرار المالك بتاريخ 2026-10-16.

## 7. حزمة إعداد المالك — مرة واحدة فقط

حتى لا تتكرر الطلبات أثناء العمل، يتم تجهيز ما يلي مرة واحدة وتوثيق حالته دون قيم سرية:

| البند | أين يتم؟ | ما الذي أحتاجه من المالك؟ |
|---|---|---|
| GitHub | حساب مالك المشروع | إبقاء المستودع والإصدارات تحت حساب المشروع وتمكين Actions/Pages |
| Cloudflare | حساب المشروع | تسجيل دخول Wrangler بالمتصفح مرة واحدة على جهاز المالك |
| Supabase | مشروع المشروع | تنفيذ الترحيلات أو تشغيل أداة التهيئة من حساب المالك |
| مفتاح `service_role` | Cloudflare Worker Secret فقط | المالك يلصقه في موجه مخفي على جهازه، ولا يرسله في المحادثة |
| Resend SMTP | Supabase Auth | المالك يدخل بيانات SMTP في لوحة Supabase |
| نطاق وبريد رسمي | عند الإطلاق | قرار شراء/ربط لاحق، وليس شرطاً لإثبات الأساس |

### قاعدة الأسرار النهائية

- المفتاح العام Publishable/anon يمكن أن يوجد في الواجهة لأنه محمي بـ RLS.
- `service_role` وأي API Token رئيسي لا يدخلان المحادثة ولا GitHub ولا البلجن ولا الموقع.
- هذا ليس رفضاً للعمل؛ كل ما يمكن بناؤه واختباره ونشره من الكود سيتم من طرفي.
- الجزء الوحيد الذي يجب أن ينفذه المالك هو إدخال السر داخل لوحة/موجه الجهة الرسمية نفسها، لأنني لا أملك جلسة متصفح مسجلة باسمه ولا يجب أن أستلم كلمة السر أو مفتاح السيطرة على حساباته.
- أي سر يظهر في محادثة أو لقطة يعتبر محترقاً ويتم تدويره مرة واحدة ضمن حزمة الإعداد، لا في كل مهمة.

## 8. قواعد العمل من الآن

1. لا ميزة جديدة دون مشكلة/هدف ومعيار قبول واختبار.
2. لا إصلاح من أول رسالة خطأ؛ يتم التكرار والتشخيص والسبب الجذري أولاً.
3. لا نشر يدوي غير موثق، ولا إصدار دون رقم نسخة وسجل تغييرات.
4. لا رسالة خطأ للمستخدم تكشف Supabase أو Cloudflare أو قاعدة البيانات.
5. لا طلبات متفرقة من المالك؛ أي احتياج حسابي يجمع في قائمة إعداد واحدة قبل بدء المرحلة.
6. كل مرحلة تنتهي بتقرير قصير: ما تم، ما اختبر، ما تبقى، وما يحتاج قراراً.
