# خطة الربط عبر Subusers — إعادة تخطيط كاملة (2026-10-17)

> هذه الخطة تلغي التخطيط السابق لمسار البوت داخل اللعبة كمسار أساسي، وتعتمد فكرة المالك: حساب للمنصة داخل الاستضافة + صلاحيات Subuser.

## 1) الفكرة كما وردت من المالك (منظمة بالحرف)
1. إلغاء البلجن نهائيًا (تم فعليًا في الإصدار السابق).
2. المستخدم يضغط زر ربط السيرفر.
3. المنصة تطلب رابط الاستضافة المراد ربطها.
4. تطلب إيميل مؤقتًا + باسورد + تأكيد الباسورد.
5. المنصة تتوجه إلى رابط الاستضافة وتنشئ حسابًا هناك بهذه البيانات.
6. تطلب من المستخدم اسمًا للحساب، وتعتمد اسم الحساب.
7. تطلب من المستخدم منح الحساب صلاحيات عبر Subusers داخل لوحة الاستضافة.
8. المنصة تتحقق: إن ظهر السيرفر على حسابها، تنقل المستخدم إلى شات الـ AI؛ وإن لم يظهر، تنتظر وتبقى تحاول.

## 2) لماذا Subusers هو المسار الصحيح
- أغلب منصات الاستضافة أغلقت رفع البلجنات يدويًا، لكن Subusers ميزة رسمية مدعومة.
- الصلاحيات رسمية وقابلة للتحديد بدقة من مالك السيرفر نفسه، وقابلة للإلغاء الفوري بحذف الـ Subuser (مفتاح إيقاف حقيقي بيد المالك).
- تمنح المنصة قدرات أعمق من أي مكوّن داخل اللعبة: كونسول (عرض + إرسال أوامر)، تشغيل/إيقاف/إعادة، وقراءة ملفات وسجلات حسب الصلاحيات الممنوحة.

## 3) نتائج البحث (2026-10-17)
| الاستضافة | Subusers | الدليل | التنفيذ التقني |
|---|---|---|---|
| FalixNodes | ✅ موثقة رسميًا | دليل Sub-Users: صلاحيات Console Access وSend Commands وأدوار جاهزة، والإضافة بإيميل/اسم مستخدم مسجل عندهم | لوحة خاصة — محوّل خاص |
| play.hosting | ✅ معلنة | الصفحة الرئيسية تذكر "Invite subusers" ضمن مزايا كل سيرفر | يفحص عمليًا في Phase 0 |
| لوحات Pterodactyl عمومًا | ✅ موثقة | صلاحيات websocket.connect (تلقائي) وcontrol.console/control.start/stop/restart، وClient API بمفتاح ptlc_ وWebSocket للكونسول وأمر POST ‎/command | محوّل Pterodactyl عام |
| Minefort | ⚠️ غير مؤكد | لم نجد توثيق Subusers (لوحة خاصة وكونسول خاص) | فحص عملي Phase 0 |
| MCServerHost | ⚠️ غير مؤكد | يحتاج فحصًا عمليًا | فحص عملي Phase 0 |

## 4) التدفق المعتمد (حالات رسمية)
LINK_STARTED ←(رابط الاستضافة) ACCOUNT_CREATING ←(إنشاء الحساب) ACCOUNT_READY
←(اسم الحساب المعتمد) WAITING_FOR_SERVER «بانتظار ظهور السيرفر على الحساب»
←(منح صلاحيات Subuser) PERMISSION_CHECK ← VERIFIED ← فتح شات الـ AI
- في WAITING_FOR_SERVER: المنصة تسجل دخولها بحسابها وتفحص قائمة سيرفراتها دوريًا. لو لم يظهر السيرفر: تبقى منتظرة وتعيد الفحص تلقائيًا (رسالة حالة واضحة + زر «تحقق الآن»).
- PERMISSION_CHECK: تجربة غير مؤذية (قراءة حالة/كونسول) للتأكد أن الصلاحيات المطلوبة ممنوحة فعلًا.

## 5) كيف تتصل المنصة تقنيًا
- بيانات حساب المنصة على الاستضافة (إيميل/باسورد) محفوظة مشفرة AES-GCM كما في هجرة 008 — يعاد استخدام الخزنة الحالية.
- التحقق من الظهور: تسجيل دخول الحساب ثم سرد السيرفرات المتاحة له (Client API/جلسة اللوحة حسب الاستضافة).
- التنفيذ لاحقًا: إرسال أوامر القوالب المعتمدة فقط عبر كونسول اللوحة (WebSocket أو ‎POST /command‎ في Pterodactyl) مع قراءة الإخراج كدليل نتيجة — نفس فلسفة القوالب المعتمدة الحالية، بدون نصوص حرة.
- أقل صلاحيات نطلبها من المستخدم: عرض الكونسول + إرسال الأوامر (+ بدء/إعادة التشغيل). قراءة الملفات مرحلة تشخيص لاحقة بصلاحية إضافية اختيارية.

## 6) خطوة إنشاء الحساب على الاستضافة (تصميم صادق)
- المنصة تجهز البيانات وتدير الخطوة برمجيًا حيث تسمح الاستضافة (نماذج/واجهات تسجيل متاحة).
- بعض الاستضافات تفرض تحققًا بشريًا (CAPTCHA/تأكيد بريد) لا يجوز تجاوزه؛ عندها يكمل المستخدم ضغطة التحقق فقط في صفحة الاستضافة بالبيانات التي جهزتها المنصة، ثم تتولى المنصة الباقي والتحقق. هذا فرع تصميم لكل استضافة، ويُحسم بنتيجته في Phase 0 لكل استضافة على حدة.

## 7) المراحل ومعايير القبول
- **Phase 0 — فحص عملي (Spike):** حسابات تجريبية على FalixNodes وplay.hosting؛ إضافة Subuser؛ إرسال أمر كونسول من سكربت خارجي؛ التأكد من ظهور السيرفر على حساب المنصة. القبول: سجل نجاح موثق لكل استضافة (أو توثيق العائق بدقة).
- **Phase 1 — الربط:** معالج جديد (رابط ← بيانات حساب ← اسم ← انتظار الظهور ← تحقق صلاحيات) لأول استضافة ناجحة في Phase 0. القبول: ربط حقيقي كامل من الموقع حتى فتح الشات.
- **Phase 2 — التنفيذ من الشات:** نقل القوالب المعتمدة السبع إلى كونسول اللوحة مع نتائج موثقة من إخراج الكونسول.
- **Phase 3 — التوسع:** play.hosting وPterodactyl العام، ثم MCServerHost وMinefort حسب نتائج الفحص.
- **Phase 4 — العمق:** قراءة سجلات/ملفات للتشخيص، إعادة تشغيل، وإدارة يومية موسعة حسب الصلاحيات.

## 8) أمان ومخاطر
- تشفير بيانات حساب الاتصال، وعدم ظهورها في الواجهة أو السجلات.
- لا نطلب أبدًا باسورد حساب المستخدم الشخصي في الاستضافة — بيانات جديدة مخصصة لحساب المنصة فقط.
- المخاطر: CAPTCHA/تأكيد بريد عند التسجيل، 2FA (نطلب عدم تفعيله على حساب المنصة)، تغيّر واجهات اللوحات (محوّلات معزولة لكل استضافة)، حدود زمن جلسات التشغيل.

## 9) مصير البناء الحالي
- يبقى: خزنة بيانات الاعتماد المشفرة، حالات الربط، المعالج، قوالب الأوامر المعتمدة، الشات.
- يتحول المشغّل من «بوت داخل اللعبة» إلى «مشغّل لوحات» (Panel Runner) يفحص الظهور وينفذ عبر الكونسول.
- مسار البوت داخل اللعبة: مؤرشف، ليس مسارًا أساسيًا.
